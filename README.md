# Handmade Mortar & Pestle Store

[![CI](https://github.com/Danielyarva/project/actions/workflows/ci.yml/badge.svg)](https://github.com/Danielyarva/project/actions/workflows/ci.yml)

A responsive e-commerce website for a handmade mortar and pestle business, built as a
MERN-stack portfolio project. See `CLAUDE.md` for the full tech spec and `DESIGN.md`
for the design system.

## Tech Stack
- **Client**: React (Vite), TypeScript, Tailwind CSS
- **Server**: Node.js, Express, TypeScript
- **Database**: MongoDB (Atlas) via Mongoose
- **Payments**: Stripe Checkout
- **Images**: Cloudinary
- **Email**: Resend
- **Testing**: Jest + Supertest (server), Vitest + React Testing Library (client)
- **CI**: GitHub Actions (`.github/workflows/ci.yml`) — lint, typecheck, test, and build on every push

## Project Structure
```
client/   React frontend
server/   Express API
```

## Local Setup

### Prerequisites
- Node.js 20+
- A MongoDB Atlas cluster (free tier is fine) and its connection string

### Server
```
cd server
cp .env.example .env   # fill in MONGO_URI with your Atlas connection string
npm install
npm run dev             # http://localhost:5000
```

### Client
```
cd client
cp .env.example .env
npm install
npm run dev             # http://localhost:5173
```

The client dev server proxies `/api` requests to `http://localhost:5000`, so both
should be running together during development.

### Running tests
```
cd server && npm test        # Jest + Supertest
cd client && npm test        # Vitest + React Testing Library
```

## Deployment

The app deploys as two separate services — a static frontend and an API — plus three
third-party accounts the app depends on. None of this can be done from a CLI session
alone: each step below requires signing into the relevant dashboard yourself.

### 1. Third-party accounts (do this first)

| Service | What you need | Where it's used |
|---|---|---|
| [MongoDB Atlas](https://cloud.mongodb.com) | A cluster + connection string | `MONGO_URI` |
| [Cloudinary](https://cloudinary.com) | Cloud name, API key, API secret (Dashboard → Settings → Access Keys) | `CLOUDINARY_*` |
| [Resend](https://resend.com) | An API key (resend.com/api-keys) | `RESEND_API_KEY` |
| [Stripe](https://dashboard.stripe.com) | Test-mode secret key (Developers → API keys) | `STRIPE_SECRET_KEY` |

Keep these values somewhere safe — you'll paste them into Render's dashboard in step 3.
Never commit them; `.env` is gitignored and `.env.example` only documents the shape.

### 2. Frontend → Vercel

1. Import this repo into Vercel.
2. Set **Root Directory** to `client` (Vercel auto-detects the Vite framework preset).
3. Add an environment variable: `VITE_API_URL` = `https://<your-render-service>.onrender.com/api`
   (you'll get the real Render URL after step 3 — deploy once, come back and set this,
   then redeploy).
4. Deploy. `client/vercel.json` handles the SPA rewrite so client-side routes
   (e.g. `/shop`, `/products/:slug`) work on direct navigation and refresh, not just
   client-side `<Link>` clicks.

### 3. Backend → Render

CLAUDE.md allows either Render or Railway; this repo ships a Render Blueprint since it
only needed picking one. Railway works too — Nixpacks auto-detects the Node app if you
set the service's root directory to `server` and add the same environment variables
listed below by hand; there's just no `railway.json` checked in for it.

`render.yaml` at the repo root is a [Render Blueprint](https://render.com/docs/blueprint-spec) —
Render can read it directly:

1. New → Blueprint → connect this repo. Render will detect `render.yaml` and propose
   a `mortar-pestle-api` web service rooted at `server/`.
2. `JWT_SECRET` is auto-generated by the blueprint. Every other variable is marked
   `sync: false`, meaning Render will prompt you to fill it in rather than storing a
   value in the repo — fill in the Atlas/Cloudinary/Resend/Stripe values from step 1,
   plus `CLIENT_URL` = your Vercel URL from step 2, and `EMAIL_FROM` /
   `CONTACT_NOTIFY_EMAIL` (see `server/.env.example` for what these mean).
3. Deploy. Render builds from `server/` (`npm ci && npm run build`) and runs
   `npm start`, health-checked at `/api/health`.
4. Once you have the real Render URL, go back to Vercel and set `VITE_API_URL` to it,
   then redeploy the frontend so it stops pointing at localhost.

### 4. Stripe webhook (do this after the backend is live)

The backend needs a real, publicly reachable URL before Stripe can send it webhook
events — this is why it's the last step, not part of account setup.

1. Stripe Dashboard → Developers → Webhooks → Add endpoint.
2. Endpoint URL: `https://<your-render-service>.onrender.com/api/webhooks/stripe`
3. Event to send: `checkout.session.completed`.
4. Stripe shows you a signing secret (`whsec_...`) — set that as `STRIPE_WEBHOOK_SECRET`
   in Render's environment variables and redeploy the backend.

### 5. Post-deploy checklist

- [ ] Visit the Vercel URL; confirm the shop loads (this proves `VITE_API_URL` → Render
      → Atlas are all connected).
- [ ] Register an account, then promote it to admin by hand in Atlas (there's no
      self-serve admin signup — see `CLAUDE.md`'s Admin Auth section) and confirm
      `/admin` works.
- [ ] Add a product with an image in the admin panel; confirm it appears on the shop
      page (proves Cloudinary is wired up).
- [ ] Submit the contact form; confirm the notification email arrives (proves Resend).
- [ ] Run an end-to-end checkout with a
      [Stripe test card](https://docs.stripe.com/testing#cards) (`4242 4242 4242 4242`,
      any future expiry/CVC); confirm the order shows "paid" and a receipt email
      arrives (proves the Stripe webhook is reachable and correctly signed).

None of this can be verified in advance from a coding session — it's the first point
in the project where the whole stack is actually connected end-to-end.

### 6. Soft launch

CLAUDE.md's build order ends with a soft launch — taking real orders on a small scale
before wider release. That's a business decision for you to make once the checklist
above is green, not something to automate.
